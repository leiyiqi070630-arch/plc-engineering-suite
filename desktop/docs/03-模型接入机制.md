# 03 · 模型接入机制

系统的模型层是**本地网关**形态：引擎只认一个 OpenAI 兼容端点，网关负责把请求翻成目标供应商的协议。
这样换供应商不需要改引擎、不需要重新打包，也不需要把密钥散落在各个进程里。

## 1. 为什么不在引擎里直连供应商

| 方案 | 问题 |
| --- | --- |
| 引擎直连各家 SDK | 每加一个供应商就要改引擎并重新发版；密钥要在引擎进程里出现 |
| 渲染进程直连 | 密钥进入前端，无法用系统级加密保护 |
| **本地网关（采用）** | 引擎只认一个端点；密钥只在主进程内存里；协议差异收敛在一处 |

## 2. 拓扑

```
引擎 ──HTTP──► 127.0.0.1:<随机端口> ──► 目标供应商
        Bearer <一次性 token>            （OpenAI 兼容 / Anthropic）
```

| 机制 | 实现 |
| --- | --- |
| 端口 | 每次启动 `listen(0)`，随机分配，不固定 |
| 进程内鉴权 | 32 字节随机 hex，作为 `Authorization: Bearer` 校验；重启即失效 |
| 端点白名单 | 仅 `GET /v1/models`、`GET /api/models`、`POST /v1/chat/completions` |
| 请求体上限 | 32 MB |
| 超时 | 180 s，`response.on('close')` 联动中止 |
| 调用方校验 | 只接受 `file:` 协议且路径含渲染主文档的 frame |

引擎拿到的环境变量是 `OPENAI_API_KEY=<一次性 token>` + `OPENAI_BASE_URL=http://127.0.0.1:<port>/v1`。
它以为在调标准端点，实际打到本地网关。

## 3. 协议互转

同一份请求要能同时喂给两类供应商。

### 3.1 OpenAI 兼容

原样直发，仅按模型能力夹 `max_tokens` / `max_completion_tokens`。

### 3.2 Anthropic 原生

`requestFor()` 做完整映射：

| OpenAI 形态 | Anthropic 形态 |
| --- | --- |
| `system` / `developer` 消息 | 顶层 `system` |
| `role: "tool"` | `user` + `tool_result` 内容块 |
| `tool_calls` | `tool_use` 内容块 |
| `tools[].function.parameters` | `input_schema` |
| `stop` | `stop_sequences` |
| `tool_choice` 四态 | `auto` / `any` / `tool` / `none` |
| 相邻同角色消息 | 合并为一个 `content` 数组 |

流式方向用 `relayAnthropic()` 反向翻译：`content_block_delta` → `chat.completion.chunk`，
`input_json_delta` → `tool_calls[].function.arguments` 增量，`thinking_delta` → `reasoning_content`，
末尾补 `data: [DONE]`。

### 3.3 思考档位

不同供应商的思考强度词汇不同。网关只在**探测到服务端自报**（`status === 'reported'`）时才下发，
并用探测得到的 `effortMap` 精确翻译；没有探测结果就不发这个字段。

宁可少发一个可选参数，也不猜一个可能被服务端拒绝的枚举值。

## 4. 密钥保护

```
明文 apiKey ──safeStorage.encryptString──► base64(blob) ──► 配置文件
                     （Windows: DPAPI）
```

- 配置文件权限 `0o600`，先写临时文件再 `rename` 原子替换；
- 读取时若系统加密不可用，直接报错而不是降级成明文；
- 错误信息里出现的密钥一律替换为 `[已隐藏]`。

## 5. 配置

首次启动前放种子文件，导入后自动删除：

```
<解压目录>\data\runtime\model-provider.seed.json
```

```json
{
  "name": "自备模型",
  "baseUrl": "https://api.example.com/v1",
  "defaultModel": "your-model-id",
  "models": ["your-model-id"],
  "maxTokens": 8192,
  "apiKey": "sk-your-key",
  "protocol": "auto"
}
```

运行时配置落在 `model-provider.json`，模型能力元数据缓存在 `model-metadata.json`。

### 字段约束

| 字段 | 规则 |
| --- | --- |
| `baseUrl` | 归一化后必须可解析；换地址必须重新提供密钥 |
| `apiKey` | 禁止 `\r\n\0`；长度 ≤ 8192 |
| `maxTokens` | 夹在 256 … 131072，默认 8192 |
| `models` | 去重，上限 2000 |
| `protocol` | `auto` / `openai` / `anthropic`；`auto` 保存时落为 `openai` |

## 6. 端点探测

`discover()` 依次尝试协议与端点组合，拿到模型清单后与内置能力表合并，产出每个模型的：

- `status: 'catalog'` —— 来自内置表，思考档位按通用四档（low / medium / high / max）；
- `status: 'reported'` —— 服务端自报，用返回的 `effortMap` 精确映射。

探测失败时把密钥替换掉再抛错，避免密钥进入日志或界面。

## 7. 与引擎的分工

| 关注点 | 桌面端 | 引擎 |
| --- | --- | --- |
| 密钥 | 采集、校验、加密存储 | 只从环境变量读一次性 token |
| 协议 | 互转与流式中继 | 只发 OpenAI 兼容请求 |
| 能力 | 探测模型与思考档位 | 按注入的能力清单位置 UI 选项 |

这条分工带来一个直接好处：**换供应商不用重新构建引擎**，改配置即可。
