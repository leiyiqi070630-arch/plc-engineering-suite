# 03 · 工具目录

引擎的工具面分两层维护：**契约**（`spec/tool_contracts/`，机器可读）与**实现**（`crates/tools/`）。

## 1. 规模

| 层 | 数量 | 位置 |
| --- | --- | --- |
| 已注册工具（引擎运行时可见） | 32 | `crates/plceng-engine/src/app.rs` 的 `TOOLS` 表 |
| 完整契约（name / inputSchema / permission） | 32 | `spec/tool_contracts/tools/<name>.json` |
| 契约索引 | 32 | `spec/tool_contracts/TOOLS.md` |

运行 `plceng-engine tools` 可随时查看当前注册表，`plceng-engine tools --output-format json` 输出机器可读版本。

## 2. 权限模型

| 权限 | 含义 | 数量 |
| --- | --- | --- |
| `ReadOnly` | 不执行工程写入或 IDE 改动的生成 / 读取操作 | 4 |
| `WorkspaceWrite` | 写入受控工作区；不等同于提升到真实工程 | 13 |
| `DangerFullAccess` | 高风险写入或 IDE 操作；必须满足工具的显式确认契约 | 15 |

权限以每个工具契约的 `permission` 字段为准。不要仅凭工具名称判断风险；写入类工具应逐项检查 `confirm`、`disposable` 等必填条件，并在执行后核对结构化回执。

## 4. 契约文件怎么用

```jsonc
{
  "contract": {
    "name": "mitsubishi_csv_generate",
    "description": "Generates CSV from a structured plan. Inputs: family, project_name, rungs. ...",
    "permission": "ReadOnly",
    "inputSchema": {
      "additionalProperties": false,
      "properties": {
        "family": { "type": "string" },
        "project_name": { "type": "string" },
        "rungs": { "type": "array", "items": { "type": "object", "properties": { ... } } }
      },
      "required": ["family", "rungs"]
    }
  }
}
```

- `inputSchema` 是 **权威签名**，直接可用于生成调用方、做参数校验、或生成 IDE 插件。
- `permission` 决定这个工具能不能进批处理。
- 契约只描述接口，不描述行为；行为约束写在实现模块的文档注释里。

## 5. 新增一个工具

1. 在 `crates/tools/src/builtin_specs/<域>.rs` 声明（名称、描述、schema、权限）。
2. 在 `crates/tools/src/tool_dispatch/<厂商>.rs` 注册路由。
3. 在 `spec/tool_contracts/tools/<name>.json` 落一份契约。
4. 在 `crates/plceng-engine/src/app.rs` 的 `TOOLS` 表加一行（让运行时可见）。
5. 补一条 `plceng-engine tools` 的回归确认。


## 6. 注册表一致性检查

工具索引、单工具 JSON 契约、CLI 能力清单和本文档需要保持一致。修改工具名称、参数或权限后，在 `engine/` 目录执行：

```bash
python scripts/check_tool_registry.py
```

该检查会核对 32 份单工具契约、`tools_index.json`、`app.rs` 的 CLI 能力表，以及两份工具目录 Markdown。它是静态一致性检查，不替代真实 IDE 导入、编译或仿真验收。
