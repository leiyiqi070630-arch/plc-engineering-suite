# 02 · 模块划分

`crates/tools` 是引擎的主体（310 个模块），按职责分成四层，外加若干支撑域。这个划分不是事后总结，
而是代码目录本身的结构。

## 1. 四层结构

```
builtin_specs/        ① 声明：工具名、描述、schema、能力边界
tia_openness_inputs/  ② 校验：入参规范化、互斥/必填检查
tia_openness_tools/   ③ 执行：真正调外部执行器、解析回执
tool_dispatch/        ④ 路由：工具名 → 实现，按厂商分流
```

为什么分四层：

- **声明与实现分离**：`builtin_specs` 是给模型看的（schema + 边界话术），改提示词不动实现；
- **校验集中在 inputs**：同一个工具族共享参数约定（如 `project_match`、`confirm`），避免每个实现重复；
- **执行层不关心被谁调用**：`tia_openness_tools` 里的函数既能被 dispatch 调，也能被 batch 调；
- **dispatch 只做路由**：厂商差异收敛在一处，新增厂商不影响既有工具。

## 3. 新增一个工具的完整流程

1. **声明**：在 `builtin_specs/<域>.rs` 加 spec（name、description、inputSchema、permission）。
   描述里必须写清「支持什么形状 / 不支持什么形状 / 验收字段」。
2. **校验**：在 `tia_openness_inputs/<域>.rs` 加参数规范化（默认值、互斥、必填）。
3. **执行**：在 `tia_openness_tools/<域>/` 实现，调用外部执行器并解析回执。
4. **路由**：在 `tool_dispatch/<厂商>.rs` 注册 `工具名 → 实现`。
5. **契约**：把 spec 序列化进 `spec/tool_contracts/`，生成 `contractHash`。
6. **用例**：在 `spec/corpus/plc-generator-corpus/cases|evidence` 补一对输入输出与实测证据。
7. **回归**：确认 `--allowedTools <name>` 能单独启用，且 `agents`/`skills` 清单不受影响。

## 4. 命名约定

- 工具名 `<厂商>_<对象>_<动作>`：`tia_openness_read_hardware_config`、`codesys_pou_upsert`、
  `weinview_screen_read`。
- 错误码全大写 + 前缀：`TIA_*`、`CODESYS_*`、`PLC_*`。
- 回执里区分档位：`ok` / `warnings` / `errors` / `acceptanceVerdict` / `evidence`。
