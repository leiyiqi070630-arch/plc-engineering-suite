# PLC 控制逻辑设计与审查（按需）

适用于 TIA LAD/SCL、汇川、CODESYS 和文件交付。本文是设计参考，不是强制框架；用户需求、现有项目接口、当前工具契约和目标平台证据优先。示例是扫描语义说明，未经厂商编译或实机验证，不能直接作为可投产程序。不要为简单网络新增运行模式、故障体系或多层 FB。

## 按控制问题选用方法

同一工程可以组合多个专题；控制问题与厂商、语言是不同维度。先使用当前任务涉及的原则，缺少具体做法时再读相应段落。无状态换算可以用函数，简单联锁可以用直接逻辑，周期调节不必写成步进流程；按平台能力表达，不统一套用状态机或Execute/Busy/Done接口。

| 专题 | 需要核对的关键点 |
|---|---|
| 离散逻辑、泵阀联锁 | 信号极性、同时命令优先级、锁存释放、反馈不一致、最终输出归属 |
| 顺序、配料、批次 | 步骤进入/退出、条件互斥、分支汇合、暂停重入、重复加工/计数 |
| 定时、计数、事件 | 沿与电平、实例寿命、定时器复位、任务周期、累计范围、高速采集机制 |
| 模拟量、计算、数组 | 单位与量程、数据类型/精度、转换顺序、分母/索引/溢出边界、输入有效性 |
| PID、连续过程 | 采样周期、控制方向、量程和输出限制、传感器异常、手自动切换及积分处理 |
| 通信、数据交换 | 数据布局、字节/字序、请求与应答关联、超时重试、过期值和重复写入的后果 |
| 配方、报警、HMI | 参数合法性、一致应用、命令仲裁、故障发生/确认/消失的区别、保存与重启 |
| 运动、驱动 | 原生绑定、当前就绪、指令全部终态、限位、真实反馈、停止与恢复 |

共同核对实际任务调用、数据归属和初始化；长期运行还应按需检查计数/时间范围和资源增长。一次小改动只检查受影响路径，不要求把所有专题全量执行。

跨任务共享队列、配方或复合数据时，分别检查正常提交和复位/取消/重连。每个变量只有一个写者，不等于多个变量组成的事务一致；条件复核之后仍可能被抢占。例如消费者通过最后一次检查后，生产者复位发布计数，消费者恢复又提交旧取数，会破坏满空关系。应使用目标支持的同步原语或有确认阶段的协议，明确各方何时停止旧事务、何时恢复。非阻塞锁失败时要保留或明确拒绝本次命令及配套数据；高优先级任务不得忙等一个只能由低优先级任务释放的锁。参考 [CODESYS 原子比较交换](https://content.helpme-codesys.com/en/CODESYS%20Development%20System/_cds_operator_compare_and_swap.html)，具体类型、内存顺序与目标支持仍须核对，不把“同优先级”当通用互斥保证。稳定输入仿真与静态交织分析分别记证据。

延迟处理还要保留请求在采样时是否有效及其所属代次，不能只保存载荷：禁用时采到的输入沿，不能在后来使能、取得锁后补收；有效请求被禁用或复位取消时应明确作废。已受理的复位若被锁延迟，应完成交接后再接受新一轮运行，或按既定接口明确报告取消，不能静默丢掉却宣称复位成功。分别检验“事件到来时取锁失败→输入改变→下一拍提交”，以及等待槽已有请求时又来新事件；保留或拒绝都应符合原需求，不能用延长按钮电平掩盖丢事件。

## 数据、闭环、通信和参数的短例子

任务优先级不等于同核运行。CODESYS/汇川先用 `task_list` 读取实际 `core_binding`；默认负值不能自行解释成指定核心。若算法依赖同核抢占顺序，显式设置并保存重开核对，同时确认目标运行时的调度配置。跨核共享复合状态优先使用目标实际支持的原子同步或完整握手；存在 `__COMPARE_AND_SWAP` 文档不等于当前设备已支持，应编译并验证成功/失败两分支。配置读回、静态交织分析和仿真观测分别说明，不把普通轮询通过当成任意时刻均安全。

以下是说明性思路，具体类型、指令和接口以目标平台为准。

- **量程换算**：`(raw - low) / (high - low)` 若先按整数计算，后面转REAL已经丢失小数；无符号相减还可能先发生下溢。先验证量程并转换参与运算的操作数，再计算比例及工程量。分母为零、输入超范围、传感器无效分别按接口约定处理；不能只把最终值钳在范围内就报告测量有效。区分原始值、工程值和质量位。
- **闭环调节**：任务里每次调用PID不证明其采样周期参数正确。核对实际任务/调用频率与库的周期约定、调节方向、输出上下限、手动值和切换方式；传感器失效后的输出取决于工艺。积分限幅/跟踪先查所用控制器接口，不猜一个同名引脚。使用软件对象模型验证时，保留模型方程、采样周期和外部扰动假设，不能将其称为物理设备调试完成。
- **无扰切换与抗饱和**：自写 PI 时，输出 `P+I+偏置` 的允许范围与积分状态的允许范围不是同一件事。无扰接管需要积分/跟踪状态补偿当时的比例和偏置；例如手动10%、P=200时，I=-190才能接管，随后把I固定夹到±100会破坏该关系并突跳。这个反例已在汇川20ms仿真测到；修正算法仍须检查大正/负误差、不同手动值、饱和退出和失效测量恢复。使用库时查其跟踪/切换接口，不把这个代数例子当成所有PID库的引脚写法。方法依据：[MathWorks 无扰切换](https://www.mathworks.com/help/simulink/slref/bumpless-control-transfer-between-manual-and-pid-control.html)；不代表现场闭环性能已经验收。
- **通信数据**：收到字节或连接成功不代表本次事务有效。按协议验证目标、功能/类型、长度、请求标识及数据解释；晚到或旧应答不能覆盖新请求的结果。对写入/触发命令，重试前考虑接收方是否可能已经执行。过期数据可以按需求保留显示，但质量/时间戳必须反映已过期。输入报文仿真只证明解析/事务逻辑，不证明实际端口、总线或设备互通。
- **配方与参数**：逐个把HMI暂存值写入活动参数，可能让运行逻辑读到半套新配方。先检查待应用数据的完整性、范围及组合约束，再在约定时刻一致应用；校验失败保留原活动配方并给出原因。是否允许运行中切换、哪些值要保持，由需求决定，不默认全部RETAIN。
- **报警**：发生条件、活动状态、需确认状态和历史记录是不同含义。确认按钮不自动消除仍存在的故障；条件消失后是否自动恢复/仍需确认依报警类别决定。去抖、回差和延时按信号及工艺需要选择，不能给所有报警硬套同一个锁存。

## 先确定行为，再选择写法

只为当前任务确定这些信息：输入有效电平；命令和真实反馈；每个输出的唯一负责位置；跨扫描状态及掉电保持；时间单位/范围；停止、故障、复位和恢复方式。沿用项目命名和接口。影响功能的未知条件才需要一次集中提问，其余用明确假设推进。

| 需求 | 合适的表达 | 容易写错的地方 |
|---|---|---|
| 点动，松手停止 | 电平请求经过允许和互锁 | 额外自锁导致松手不停 |
| 启动脉冲后持续运行，停止优先 | 停止优先的运行记忆或状态 | 两个独立 IF 让后面的启动覆盖停止 |
| 持续使能 | 根据需求定义允许恢复后的响应 | 默认改成沿触发，或擅自恢复运动 |
| 故障确认 | 原因消失后按指定确认方式清除 | 把 Reset 当 Start，或故障仍在时短暂清除输出封锁 |
| 顺序动作 | 命名状态、转换条件、实际到位反馈 | 连续 IF/梯形网络在同一扫描穿越多个状态 |
| 等待人工操作 | 可以无期限等待 | 为所有等待强加超时故障 |
| 有时限的动作 | 独立超时及规定的退出动作 | 把输出命令当成执行完成反馈 |

锁存、自动复位、停止后的继续/重来都由需求决定。不要强制三种模式、所有报警锁存或所有执行器失电：例如夹持、冷却和制动可能有不同的安全状态。

## 扫描顺序示例：延时后点亮状态灯

假设：Start 上升沿启动；PermitOk 丢失或 Stop 有效立即回 Idle；恢复允许后需要新的启动沿；等待 Delay 后进入 Active。Start 上电已为真是否算新沿应由启动规则另行定义。灯不是电机或安全功能。

下面是 ST 风格伪代码；Idle/Waiting/Active 是命名状态，state、startEdge、waitTimer 为持久实例/状态，nextState 为本扫描工作值。使用目标平台允许的类型和调用方式。

```text
startEdge(CLK := Start);                         // 所有扫描调用，包含释放扫描
waitTimer(IN := (state = Waiting) AND PermitOk AND NOT Stop,
          PT := Delay);                         // 退出/停止时仍执行 IN=FALSE
nextState := state;

IF Stop OR NOT PermitOk THEN
    nextState := Idle;                          // 停止优先，后续 CASE 不再覆盖
ELSE
    CASE state OF                              // 只基于扫描开始时的 state
        Idle:    IF startEdge.Q THEN nextState := Waiting; END_IF;
        Waiting: IF waitTimer.Q THEN nextState := Active; END_IF;
        Active:  ;                             // 等待停止
        ELSE     nextState := Idle;            // 非法状态的处置；按需报告诊断
    END_CASE;
END_IF;

state := nextState;                             // 一次提交状态
Lamp := (state = Active) AND PermitOk AND NOT Stop; // 唯一最终输出赋值
```

这个顺序在进入 Waiting 的下一扫描才使能定时器，必须把最多一个任务周期的启动偏移纳入时间验收；精确时序需求可以采用另一种明确的调用顺序。状态改变后也不能跳过定时器的下一次调用。TOF/TP/保持型定时器的输入与复位语义不同，不能套用 TON 的结论。

LAD 中可用状态快照/下一状态或等效互斥结构：关键是前一网络写入的新状态不能意外触发后面网络再次前进。不要简单要求所有位只能写一次：内部工作量先默认再按优先级覆盖是合法设计；物理输出应在集中仲裁后写入。

## 设备块与可维护性

- 小程序用清楚的网络即可；设备重复出现、有独立状态或接口复用需求时再封装 FB/子程序。平台不支持 FB/枚举时使用其子程序、持久存储和命名常量，不跨品牌照搬语法。
- 参数集中，带单位与合法范围，例如启动延时、反馈超时、模拟量量程。不要为抽象而拆出大量只转发参数的小块。
- 分开 `StartRequest`、`RunCommand`、`RunningFeedback` 和 `FaultActive`；输出命令不能冒充实际反馈。暴露当前状态、阻塞原因和适用的故障编号，便于在线定位。
- 正反转/开关双阀等相反动作必须先处理命令冲突，必要时等待实际对侧释放和中性间隔；手动和自动共用最终互锁，不能各写一次物理输出。
- 注释解释工艺目的、优先级、单位、恢复条件。网络标题表达“一件事”，如“停止优先的运行请求”，不只写“网络 3”。
- IEC CTU/CTD 等通常已经检测计数输入的边沿；先读实际指令语义，再判断是否需要额外整形/去抖，不能声称所有计数器输入为高就每扫描加一。

## 从需求独立导出验收

较大工程先沿真实输入走通一个有代表性的执行单元，再扩展复用。查看实际任务调用顺序和原生块内容，不能以“变量表有这个点”“块已创建”代替接线完成。物理按钮与 HMI 命令若共享仲裁，分别追到消费者与最终输出；模拟内部命令只证明该内部接口之后的路径。

跨块异步操作要辨认本次请求、受理、完成或中止。上次留下的 Done 不能结束刚发出的新请求；设备故障清除与软件超时锁存清除不能互相作为永远无法满足的前提。暂停、停止的约定要传到正在执行的站、轴或通讯事务，不能只停止新增派发。

请求使能不等于设备已经就绪。按当前平台的真实反馈确认执行前置；尚未就绪时可以排队或明确拒绝，不能吞掉唯一请求沿后永久等待。恢复、重新使能或重建连接后，应重新核对本次操作所需的就绪状态，历史 HomeDone/Connected/Done 锁存不能替代当前反馈。错误码先对应 CPU、库和版本查原始定义，再同步观察使能、停止/中止、请求受理与完成；不能把一个运动错误猜成“丢回零”后反复复位或回零。

区分暂存未受理请求与撤销后重新请求。失能或未就绪时仍要处理请求撤销、检测器复位和受理记忆；把整个边沿检测放在就绪分支里，可能漏掉这期间的低电平，使恢复后的新请求被历史高位屏蔽。结合本次请求、受理编号和取消路径检查，不以“现在已就绪”推断新命令已经受理。使用持续电平、边沿或事务编号均可，按接口约定选择。

物料持有、工序完成、合格判定和数量入账是不同事实。以一次真实交接为单位核对请求、接收、确认与撤销/重新就绪；入口传感器保持有料不应自动代表新件持续到来。故障复位、维修退出、回零完成、模式切换或重启时，都要将下一工步与在制事实、已完成工序、交接确认相互核对。保留在制位却回到只接收新件的空闲等待，可能造成永久阻塞；无条件重做也可能重复加工或计数。继续、退回或人工处置由工艺约定决定，不能用统一“回到初始状态”代替恢复策略。单步或下游等待期间，一次性计数/出库/派发不能随扫描重复；不同实现均可，只要接口与行为吻合。

工艺结果已经提交，也不代表机械动作已收尾、工件已能交接。例如加工计数可能早于松夹、退刀、回安全位或撤销送料命令。恢复时保留已完成的工艺与计数，同时完成仍欠缺的机械步骤并复核反馈，之后才允许交接；不能为了防重复加工就直接跳到出料态。分别检查“未加工”“已加工但未完成机械收尾”“已收尾待交接”，这些是区分前置的思路，不要求所有程序采用固定三态。故障、维修、模式切换等不同恢复入口要逐条追到最终输出，复制相同分支不证明恢复正确。

保持性审查要读声明和启动代码两处。被标为 RETAIN/PERSISTENT 的参数如果在每次首扫描都写默认值，在线调参仍会被覆盖；不可改的定义、可调机器参数和活动配方应按实际需求分别确定初始化/恢复策略。握手的“已消费”标志是否可清除，要结合在制身份与当前物料信号判断，不能只凭它是布尔量就当瞬态。仿真复位验证不等于真实掉电保持性验证，报告应注明所用复位方式和观测时刻。

仿真验证先读当前工步、保持区、物料和计数基线；再次下载或停止/启动不等于清空了先前测试状态。必要时在独立副本和新仿真实例建立可解释的基线，同时另外验证在线修改/保持性恢复。按物理过程依次提供夹紧与松开、到位与离位等互相一致的反馈，列明外部质量信号、虚拟设备等测试假设。前置失败后不继续把依赖步骤当有效反例；诊断用读取工具，不用不可能的期望值制造假失败。新的基线测试通过也不能倒推出旧失败只有一个原因。

| 场景 | 观察与判据 |
|---|---|
| 冷/热启动、无启动命令 | 初态、输出与保持区符合指定启动策略 |
| Start 持续多扫描 | 一次性动作不重复；点动/持续允许按电平执行 |
| Stop 和 Start 同时有效 | 约定的停止优先；后续网络不重新置位 |
| 故障仍在且按 Reset | 不出现一扫描的重新允许运行 |
| 允许丢失又恢复，Start 仍高 | 符合明确的重启策略，不由代码偶然决定 |
| 定时状态退出并再次进入 | 根据定时类型复位/保持，不继承意外的 Q/ET |
| 延时前后边界 | 不提前完成，在任务周期容差内完成；不能只看最终 TRUE |
| 方向请求同时或交替有效 | 输出始终互斥；释放反馈/中性间隔有效 |
| 非法状态、传感器矛盾/不到位 | 有确定的输出和诊断处置 |
| 物料尚未加工时故障，原因解除后复位 | 恢复到约定的可执行状态，未加工件不被标成完成/合格，不凭空增加物料 |
| 有在制品时进入并退出维修/模式切换 | 按未加工、已加工待交接等事实恢复；既不等待不存在的新来料，也不重复加工或入账 |
| 工艺已完成但松夹/退回尚未完成时恢复 | 保留工艺结果和已计数量，交接仍等待当前机械反馈及互锁，不能跳过收尾 |
| 设备重新使能或连接恢复，命令仍有效 | 根据当前就绪状态受理、排队或明确拒绝；不使用上次完成位代替本次结果 |
| 调参后执行规定的重启/复位 | 核对声明、启动默认写入与实际保留值；上料持续信号不应凭空产生新身份 |
| 单步、暂停、下游阻塞跨越多个扫描 | 等待期间不重复计数或交接；恢复后本次工作不遗漏 |
| 完整正常周期与再次启动 | 经实际输入走通处理、交接、收尾与重新就绪；逐步观察不能只看最终状态 |
| 局部修改 | 原有接口、任务调用、未修改网络与行为保持 |

静态审查说明“从文本推导”；导入/读回说明“结构已落地”；编译说明“目标接受”；仿真/实测需记录独立输入、实读值、时间与通过/失败结果。先确认反例的前置状态真的成立，按完整场景判定结果，不能从几个失败场景中摘取通过步骤凑成全通过。没有运行证据就不写“已验证运行正常”。

只读观察步骤可以验证前一次刺激后的自然推进，缺少本步骤写入不等于缺少复位。工具的诊断建议也需与回执和代码核对；故障末尾的失能、超时等状态可能是停机的结果，应查看失败前的共同观测，避免把后果当起因。

依据：以上是针对本产品的设计建议；物理输出单点写入及可读性参考 [PLCopen Coding Guidelines](https://plcopen.org/system/files/downloads/plcopen_coding_guidelines_version_1.0.pdf)；TON 的 IN/Q/ET 语义核对 [CODESYS Standard TON](https://content.helpme-codesys.com/en/libs/Standard/Current/Timer/TON.html)。具体目标与版本仍以当前工程契约为准。


## 短窗口观测与独立测试

在线监视的标量和批量读取都可能返回缓存；调用耗时短，不等于数值新鲜。主机写入、轮询和工具往返还可能超过程序的数据有效期。验证首扫描、瞬态切换或短超时时，优先用原生 Trace，或在隔离副本中加按 PLC 周期运行的输入激励和只读记录器：业务代码保持一致，只驱动公开输入，不写输出、状态机、积分器、完成位。记录冻结后再回读，说明测试程序、调用顺序和时间依据；不要为让测试通过放宽业务超时。普通稳定状态验证不需要引入这套机制。

## 工程对照发现的具体反例

这些是2026-09-25生成工程静态审查与真实参数回读发现的缺口。下面是设计/验收要求，不把尚未执行的行为测试写成通过。

1. **停止覆盖待机和恢复**：只有运行状态处理Stop会漏掉待机Start+Stop同时到达、或恢复等待时Stop先到的情况。先仲裁Stop/取消并清除待执行启动，再允许状态推进；仅清实际输出而保留PendingMode仍可能下一拍启动。把同时命令、恢复条件随后成立、释放Stop但Start仍高分别作为独立反例。采用边沿还是电平取决于命令契约，不强行给所有输入加沿。
2. **完成计数需要事务资格**：`有WIP AND 传感器下降沿 AND (正在动作 OR Done OR Fault)` 把故障后的手动拿走也算作产出。先确认该身份曾被接受、该出料事务仍有效，再用要求的完成条件提交一次。停机/超时后的清理按取消、报废或人工确认单独处理，不复用GoodCount。测试正常完成、超时后取走、停止后取走、传感器抖动/重新放入，保持计数和WIP身份一致。
3. **交接必须落到机械输出**：分别列出发送与接收工位驱动，以及工件在哪个传感器完成交接。如果物料跨两段皮带需要两段同时运行，应检查两个真实输出；若靠重力、独立搬运机构或不同驱动契约，则按实际设计。不要因为各段都存在FB就默认传送动作完整。
4. **PID调用不等于闭环**：真实技术对象/实例工作模式和启动设置必须回读。Siemens PID_Compact对应版本的Mode、ModeActivate、Reset、ManualEnable等语义不能混用；例如V21 as-of-v2资料定义Mode=3为自动、4为手动，Reset下降沿激活所选模式。需要按该实例版本配置自动模式及启动策略，并验证State和控制输出；不把数字直接套到CONT_C或其他厂商库。实际周期OB配置需与Ts/CYCLE一致，注释“100ms”不是任务配置证据。官方参数说明：https://docs.tia.siemens.cloud/r/en-us/v21/pid-control-s7-1200-s7-1500-s7-1200-g2/pid_compact-s7-1200-s7-1500-s7-1200-g2/pid_compact-as-of-v2-s7-1200-s7-1500-s7-1200-g2/in/out-parameter-of-pid_compact-as-of-v2-s7-1200-s7-1500-s7-1200-g2
5. **质量与保护必须实际参与控制**：液位无效时，仅将质量位显示到HMI仍可能继续加热/搅拌。加热容器的温度有效不能代替液位有效和防干烧许可；加热、搅拌分别明确其最低液位与质量依赖，不能只在进料/出料步骤检查液位。按工艺定义受影响输出的允许条件、失效动作和恢复；参数校验必须保留用户给定的硬性保护上限。例如要求85度保护，不能把活动保护参数开放到95度；此数值只属于这项需求，不是所有加热工艺的通用上限。测试传感器失效与边界参数时关闭/控制测试模型的数据覆盖，避免输入刚写完又被仿真模型覆盖而误判。

6. **按真实接口连接PID模式**：PID_Compact as-of-v2 的 Mode 为 IN_OUT，调用时需要可写变量，不能把常量3接到该形参。也可按当前版本文档设置实例的模式成员；ModeActivate/Reset 的触发与优先级仍需单独验证。出现“Invalid parameter assignment”时，先对照该行形参的输入/输出/输入输出方向、可写性和数据类型，不要从相似库名猜新引脚。IN_OUT也不等于每周期强制覆盖其反馈值；模式命令与实际State应分开。
