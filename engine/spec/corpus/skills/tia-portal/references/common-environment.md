# Shared TIA environment and recovery reference

> Load this file only for TIA/Openness/PLCSIM environment setup, simulation planning, or a returned blocker code. Normal authoring requests use only the selected version/CPU reference.

## Use

- Treat current tool schemas and returned structured verdicts as the live contract.
- Run the read-only environment report once before the first simulation attempt on an unfamiliar machine.
- A trust, UAC, whitelist, or modal dialog is a pause gate. Preserve the project and session, wait for the user action, then resume the same operation.
- Do not close TIA, rebuild the project, delete objects, switch releases, or kill processes as generic recovery.
- Compile or argument failures are repairable; structural `*_NOT_SUPPORTED`, `*_NOT_EXPOSED`, and `*_UNSUPPORTED*` verdicts are final for that route.

### Blocker -> verdict -> action (say the verdict; do not re-diagnose)

When one of these appears, it already has an answer. Report the verdict and the action; do not re-probe status, do not switch simulator route, and do not rebuild or reopen the project.

| What you see | Verdict | Action |
|---|---|---|
| `Error Code: -30, LicenseNotFound` on any Advanced call (typically `PLCSIM_ADVANCED_POWER_ON_FAILED` / `PLCSIM_ADVANCED_SESSION_DAEMON_EXITED`), while status reported `runtimeManagerAvailable: true` and the CPU type is in `supportedCpuTypes`; ahead of any call, `LICENSE_SERVICE_NOT_RUNNING` / `LICENSE_SERVICE_NOT_INSTALLED` from `tia_environment_report` say the same thing before it is hit | **Two opposite causes share this one Siemens code, so the tool already probed the Windows service `almservice` (Automation License Manager) and appended a `DIAGNOSIS:` block to the error text -read that block, do not re-diagnose and do not probe again.** Service **not running / not installed** = an environment fault; the license is fine and registration itself succeeded. Service **Running** = a genuine licensing problem. | Relay the DIAGNOSIS in the user's language and act on the branch it names. Not-running/not-installed: starting a service needs an administrator, so hand over the exact commands (`Start-Service almservice`, then `Set-Service almservice -StartupType Automatic` so it survives reboot) instead of running them yourself, then repeat the identical call once. Running: report it as a real license fault (none installed / expired / instance count exceeded / dongle unplugged) -a service restart cannot fix it. Never tell a user to buy a license off the raw Siemens code. If the block says the status was unprobed (non-Windows or the query failed), have the user run `sc query almservice` before concluding either branch. |
| `list_instances` empty right after a register that returned success | Boot latency, or the holding session is gone (PLC Code restarted). Registration did not silently fail. | Re-read `list_instances` once after a few seconds. If still empty and PLC Code restarted in between, register again. Do not power-cycle, re-probe status, or report the API as broken. |
| `TIA_DOWNLOAD_TARGET_CONFIGURATION_REQUIRED` | The download was called without a connection target. Not an environment fault. | Call `tia_openness_list_online_targets` and copy `mode` / `pc_interface` / `interface_number` / `target_interface` into the same download call. |
| Download refused on a blank simulated CPU, or an explicit memory-reset requirement | TIA requires a memory reset before the first download to an empty PLCSIM target. | Re-issue with `allow_plcsim_memory_reset=true` (plus `confirm=true` and `download_confirm=true`). Do not rotate IPs or interfaces. |
| Status/route reports attachable Portals or a "running portal" basis while the version you can see does not match, or no Portal is actually open | Historic defect (fixed 2026-07-28): Siemens helper services such as `ObjectFrame.FileStorage.Server` outlive the Portal and were counted as attachable Portal instances, so routing pinned a hallucinated version -classically after a Portal crash. | On a build showing this, stop trusting auto-selection: pin `tia_version` explicitly on every call and verify the release each result reports back. Do not conclude the project moved, and do not close or restart anything to "clean" it. |
| `SIDECAR_FRONTEND_NOT_READY: The ... instance did not recover to a powered, configured state within 15 seconds after download` | **The words "after download" are part of a fixed string and do NOT mean a download happened.** The real cause is that the frontend card is still `operatingState: "UNCONFIGURED"` / `configured: false` -nothing has ever been downloaded into it, so the SIM table it wants to read does not exist yet. Compare against the `start` result you already hold: `powered: true` + `configured: false` is exactly this state. Not an environment fault, not a failed download. | Do a real TIA download into the card first (`tia_openness_list_online_targets` ->`tia_openness_download_to_device` with `allow_plcsim_memory_reset=true`, `start_after_download=true`), then repeat the identical read. Do not re-`start`, do not power-cycle, do not re-download something that was never downloaded, and do not switch simulator route. Until the download lands, the only readable surface on V18/V19/V20 is `tia_plcsim_standard_read_output` (Q image over VPLC gRPC), which works on an `UNCONFIGURED` card -real machine 2026-07-29. |
| `SIDECAR_VPLC_WRITE_REJECTED: The frontend-owned VPLC rejected the process-value write: AddressOutOfRange` on a card that has never been downloaded to | The vendor has no I/O module mapped at that address because no hardware configuration is loaded. On an `UNCONFIGURED` card **every** input offset answers this way, so it is not a hint that your offset was wrong. The VPLC host is healthy and still running -this is the runtime answering properly, not the route failing. | Download first, then retry the identical write. **Do not rotate `byte_offset`, do not rotate `area`, do not switch to a bit write, and do not report the write as landed.** |
| `SIDECAR_VPLC_BARE_AREA_UNSUPPORTED` on a V18/V19/V20 `set_process_value` with `area=memory` or `area=output` | Correct and final for this route: that runtime's `SetProcessValue` accepts an absolute address **only** for the peripheral input image. PLC Code refused locally, so the simulator was not touched. Sending it anyway is what used to kill `VplcHost.exe`. | Write `area=input` to stimulate, then `read_output` / `area=output` to observe the result. If a memory bit or an output must be set directly, switch to the V21 SIM-table route or PLCSIM Advanced. **Do not retry the same area, and do not treat this as an environment fault.** |
| `SIDECAR_FRONTEND_SIM_VIEW_MISSING` / `SIDECAR_FRONTEND_SIM_VIEW_TIMEOUT` on a `read_process_value` with `area=memory` or `area=input` | Not transient, and not an environment fault. On V18/V19/V20 only `area=output` is served by a runtime API (VPLC gRPC); `input` and `memory` are read by driving the Siemens frontend's **SIM View** through its Electron DOM, and the real V18 frontend has no such menu item (real machine 2026-07-31: a V18 S7-1200 M read answered this). On V21 *every* area goes that way, so there the same error means no process values at all. | Do not retry, and do not rotate the offset, byte count or area one by one. Prove the behaviour the way the route supports it: write `area=input`, read `area=output`. `tia_plcsim_plan`'s `capabilities` block (`read.*` plus `simViewDependency`) states per release which areas are real -read it, or re-call the plan, instead of probing. An assertion step that hit this is a test-design problem, not a program defect: move the expectation to `Q`. |
| `SIDECAR_VPLC_HOST_TERMINATED` | The `VplcHost.exe` runtime process exited mid-call; the message carries its PID and exit code. The simulator instance is gone. | Restart the simulator session (`tia_plcsim_standard_stop` then `start`) before any further read or write. Report the PID/exit code as-is; do not retry the same call against the dead host. |
| `SIDECAR_EXCEPTION: Timed out waiting for the VPLC runtime holder.` from `tia_plcsim_standard_start` | The sidecar started but its VPLC holder never reported ready inside the sidecar's own timeout. Real machine 2026-07-29: V17 + `s7-1500` + `OrderNumber:6ES7 511-1AK01-0AB0/V2.5` reproduced this, and it left **zero** stray PLCSIM/VplcHost processes behind -so there is nothing to clean up and no orphan to blame. This message carries no verdict of its own; do not read it as "PLCSIM is not installed" or "wrong route". | Retry the identical `start` **once**. If it repeats, first run `tia_plcsim_admin_flag_doctor` (read-only, no arguments, no administrator) -a `RUNASADMIN` layer on the release's PLCSIM executable produces exactly this symptom because the elevated process cannot be adopted into PLC Code's tree; repair with `tia_plcsim_repair_admin_flags(confirm=true)` and restart PLCSIM. If the doctor reports `blocked: false`, report the release/family as unavailable on this machine and offer a release whose route is already proven, rather than re-`start`ing in a loop or killing processes by name. |
| Openness rejects a freshly rebuilt bridge, or a trust dialog reappears | The Openness whitelist is keyed by **file hash**, so a rebuild invalidates it. `FileHash` is base64 SHA256 (not hex) and entries **accumulate**, so "an entry exists" does not mean the current hash is registered. Re-registering needs an administrator and writes under `HKEY_LOCAL_MACHINE`; there is **no per-user whitelist** (verified: no `HKCU\SOFTWARE\Siemens\Automation\Openness` exists, and `Users` hold read-only rights on the HKLM subtree). But an unregistered client is **questioned, not refused**: Siemens' Openness manual ("TIA Portal Openness firewall") documents that TIA prompts the user, "Yes" allows that ONE connection with no registry write and no elevation, "Yes to all" raises the UAC dialog and writes the entry, and **three refusals raise `EngineeringSecurityException`**. Entries are also keyed by **absolute path**, so a copy of the bridge registered at another path (an older repo checkout, a previous install directory) does not trust the running one. Expect this state after **every** PLC Code update, because publishing rebuilds the bridge. | Confirm with the read-only `tia_openness_check_whitelist` (no administrator needed): the verdict is `hashMatchCount > 0`, never "an entry exists". It is then a user-action gate: the runtime pauses and shows the action card; wait for confirmation and retry the exact tool. Never respond by closing TIA, rebuilding the project, or deleting generated objects. **Tell the user plainly what it costs and what is still possible.** On an account that CAN elevate, the permanent registration is one click in the desktop's simulation self-check. On an account that cannot (`tia_environment_report` reports `WHITELIST_NEEDS_ADMINISTRATOR` beside `ACCOUNT_NOT_ADMINISTRATOR` or `ACCOUNT_ELEVATION_BLOCKED_BY_POLICY`), do **not** report the TIA route as unavailable: keeping TIA Portal visible and answering its prompt with "Yes" works, once per connection, and PLC Code starts a fresh connection per operation -warn about the three-refusal cutoff. PLC Code has never driven that approve-every-time path end to end, so describe it as documented, not as verified. Until the entry is registered OR the prompt is answered, every `tia_openness_*` call is stalled, including `read_hardware_identifier` -so the `project_type_identifier` that every `tia_plcsim_standard_*` call demands is unobtainable and the simulation loop cannot start. Never invent an order number to get past it. Still usable without the whitelist, verified 2026-07-29: `tia_openness_check_whitelist`, `tia_plcsim_admin_flag_doctor`, and `tia_plcsim_advanced_status` (the bridge serves these without attaching to Openness). |
| `OPENNESS_GROUP_NEEDS_RELOGON` / `OPENNESS_GROUP_NOT_IN_SESSION` / `OPENNESS_GROUP_NOT_A_MEMBER` from `tia_environment_report` | Windows stamps group SIDs into the token **at logon**, so all three refuse every Openness connection identically. `NEEDS_RELOGON` means the account is **already in the group** -adding it again changes nothing at all. | Sign out of Windows and back in (or reboot), then re-run `tia_environment_report`. For `NOT_A_MEMBER` the report's `net localgroup "Siemens TIA Openness" "<account>" /add` comes first, but **the sign-out is not optional**: adding the account and carrying on in the same session looks exactly like never having added it. Do not re-add, do not retry the tool, do not restart TIA Portal, do not report the account as un-fixable. |
| `OPENNESS_GROUP_MISSING` on a machine that has TIA Portal, or `OPENNESS_OPTION_NOT_INSTALLED` | TIA Portal is installed but its **Openness option** is not. Openness is an installable option of the TIA Portal setup -there is no separate download, no DLL to copy, no PLC Code switch that substitutes. `OPENNESS_GROUP_MISSING` is the same fact from the other side: that setup option is what creates the group. | Relay the report's action: re-run the TIA setup for the named releases and add "TIA Portal Openness". **Do not create the Windows group by hand** -an empty group with the right name grants nothing. Meanwhile work on a release that does have it, or on the offline route; do not keep calling `tia_openness_*` to check. |
| `TIA_PROCESS_FOREIGN_OWNER` / `TIA_PROCESS_PARTLY_FOREIGN_OWNER` | The running TIA Portal belongs to another Windows account, or is elevated while PLC Code is not. Windows blocks the attach between the two processes; nothing inside either program can change it. | Have TIA Portal closed and restarted **normally, as this user** -not "Run as administrator", not from another session. **Never elevate PLC Code to match**: an elevated process cannot drive TIA's window at all (UIPI), so that trades this fault for a worse one. Retrying, reopening the project, and re-approving the trust dialog all change nothing. |
| `PLCSIM_STANDARD_NO_DRIVABLE_RUNTIME` / `PLCSIM_STANDARD_VERSION_GAP` | "S7-PLCSIM is installed" is not "S7-PLCSIM can be driven": V18+ is driven through the gRPC API in `resources\bin`, V16/V17 through the WCF runtime in `<install>\Bin`, and this code means neither layout was found in the installs present. The simulator must also match the **project's** TIA release exactly -a newer or older PLCSIM never stands in. | Take the drivable releases the report names and either move the project onto one of them or have the matching release's PLCSIM installed/repaired from its own TIA media. Do not retry against another release's simulator, and do not report simulation as generally broken -the report says which releases DO work. |
| `PLCSIM_LEGACY_WCF_SIDECAR_MISSING` | **Not a version boundary, and not a Siemens fault.** V16/V17 S7-1200/1500 ARE simulable -through PLC Code's own net48 `PlcSimLegacyWcfSidecar.exe` (real machine 2026-07-28: V16 start ->download ->RUN ->output read). This code means the Siemens side is complete and *this product's* executable is missing from the installation. | Relay it as a PLC Code repair: reinstall/repair PLC Code, or in a development tree build `tools/plcsim-legacy-wcf-sidecar` / set `PLC_CODE_PLCSIM_LEGACY_WCF_SIDECAR_EXE`. **Do not tell the user to install or repair TIA Portal or S7-PLCSIM, and do not report V16/V17 as unsupported for simulation.** If the report still lists other drivable releases, those are unaffected -say so instead of calling simulation broken. |
| PLCSIM starts but PLC Code cannot control it: `stop` / holder cleanup fails with `Access is denied`, the started PLCSIM is missing from the product's own process tree, or its UI cannot be driven; `ADMIN_FLAGS_PRESENT` from `tia_environment_report` | The PLCSIM executables were marked **Run as administrator** in `HKCU\SOFTWARE\Microsoft\Windows NT\CurrentVersion\AppCompatFlags\Layers` (value data contains `RUNASADMIN`). Siemens's own manifests are `requestedExecutionLevel=asInvoker` -**PLCSIM does not need administrator**, so the marker is a leftover. A non-elevated PLC Code can still launch the exe (ShellExecute elevates it) but can never terminate it or send it input (UIPI), so the whole lifecycle is lost. Real-machine 2026-07-29: all installed release main exes plus the PLCSIM Advanced UI carried it; after clearing, the process tree, command line, and termination all worked. | Call `tia_plcsim_admin_flag_doctor` (read-only, no administrator, no TIA version needed) for the per-entry verdict, then `tia_plcsim_repair_admin_flags` with `confirm=true` to remove it. HKCU is the user's own registry, so the repair needs no administrator; it backs the original values up to a restorable `.reg`/`.json` pair first, removes entries whose executable manifest is `asInvoker`, limits edits to PLCSIM/TIA Portal entries, keeps other layers such as `HIGHDPIAWARE`, and re-reads the registry to verify. **Restart PLCSIM afterwards** because the flag applies at process start. Keep PLC Code non-elevated and use these tools for the relevant HKCU AppCompatFlags entries. Verdicts other than `removable` are final: `machine-wide-needs-administrator` means the value is in HKLM and requires the user; `keep-vendor-requires-administrator` means the executable really does need elevation. |
| To actually RUN a WinCC Unified HMI (runtime / screen acceptance) -do not invent a method | The order is fixed, and every step already has a tool: **① compile the HMI → ② archive what TIA itself wrote (`<project>\IM\HMI\I\0\Saved\DownloadTask.xml` lists the payload; the official `Download.config` is generic and not GUID-bound) into a runtime ZIP → ③ `tia_wincc_unified_full_download` to load it → ④ `tia_wincc_unified_start_project` to start it → ⑤ look at the screen.** A load that answers `The installed Runtime version is invalid for the configured Runtime version (…). An upgrade/downgrade of the version is not possible.` is a **version boundary**: the project is configured for one Unified PC Runtime version and the machine has another, and Siemens forbids crossing it. | Use those tools instead of hand-rolling the Runtime Manager CLI. On a version boundary, hand the user the **native error text** and have them install the WinCC Unified PC Runtime that **matches the project's version**; do not change the project's version, do not retry the same archive, and do not re-probe. **Until a load succeeds, `runtimeStarted` and `visualVerified` stay false** -"compiles with 0 errors" is not "runs". |
| Binding an HMI connection to a PLC (`Partner` / `Station` / `Node`) on V16-V20 | **Openness cannot create it, and a correct address is not a substitute.** On the Unified connection object `Partner`/`Station`/`Node` are read-only in **every** version V16-V21 (no setter at all, not even private), `GetAttributeInfos()` is empty, `GetInvocationInfos()` lists only Delete/Validate, and the `Connections` creation signature accepts only `Name`. `InitialAddress` IS writable, but **a correct address is not a partner relationship**. V16-V20 have none of the V21 hardware communication service that could create one. | **Tell the user plainly that this step is theirs to do**: in TIA's connection editor create the connection with `<添加>` (the wizard fixes the partner at creation time), or start from a template project that already carries the partner. **Do not keep trying to write `Partner`/`Station`/`Node`, and do not describe this as something the API can set up -saying so strands the user.** |

### Classic HMI: verdicts that are final (do not re-probe)

Every row below was measured on a real TIA Portal (V18/V20, 2026-09-15/16). They are the traps that cost the most time, so they are answered here instead of being rediscovered.

| What you see | Verdict | Action |
|---|---|---|
| Importing a Classic screen whose number another screen already uses (`TIA_HMI_SCREEN_NUMBER_CONFLICT`, or TIA itself throwing `NonRecoverableException` while the Portal window disappears) | Screen numbers are unique **per device**. This is not a polite failure: TIA throws and **terminates the Portal process**, and every unsaved change in it is gone (measured three times). It is a clean exit, so there is no crash dump to hunt. | Read the device's screens first (`tia_openness_list_hmi_screens` / `tia_openness_hmi_tree`) and pass a free `number`; never rely on the generator's default `1`. Reopen the project and re-apply the work. |
| A Classic HMI compile that will not go below exactly one error: `Runtime settings: No start screen defined or the start screen has been deleted.` | Not a screen defect and not fixable through XML: the classic start screen is a device-level runtime setting with **no Openness write path** in V15.1-V21. | Fix everything else, then have the user set it once (HMI device > Runtime settings > General > Start screen), or start from a panel created from a master copy that already carries it. Do not hunt attribute names, XML imports, or alternate tools for it. |
| A Classic panel needs screens / text lists / graphic lists / screen templates / pop-up screens / slide-in screens created or edited | Classic HMI has **no object-level Create** for any of them - whole-document XML import is the only authoring path (those compositions expose `Import`; only folders have `Create`). | Author with `tia_hmi_generate_screen_xml` / `tia_hmi_generate_list_xml` (or edit a real export), land it with `tia_openness_import_hmi_xml`, and confirm with `tia_openness_export_hmi_xml`. Do not go looking for `Screens.Create`. |
| "Export all screens", "export all templates", or export of a folder answers `TIA_HMI_OBJECT_KIND_NOT_EXPORTABLE` / `TIA_HMI_EXPORT_METHOD_NOT_FOUND` | Correct and final: the vendor's export takes **one** object (`Export(FileInfo, ExportOptions)`), and the manual states bulk exports are not supported ("you need to enumerate and export all screen templates separately"). | Enumerate first (`tia_openness_hmi_tree`) and export each concrete object. Do not retry the folder path. |
| Writing a Classic text-list (or graphic-list) entry by hand and TIA answers `The 'Value' attribute ... is not supported` | The entry's identity is the **`From`/`To` range**, not a value attribute. `EntryType` is `SingleValue` or `Range` (both verified), `DefaultEntry` is a boolean (at most one `true`), the text is a `MultilingualText` composition named `Text`, and the composition of entries is `Entries`. | Use `tia_hmi_generate_list_xml`, or the verified shape in the capability matrix. A single value is the degenerate range `from == to`. **Do not reintroduce `Value`** - it fails validation on the entry object. |
| A Classic slide-in screen cannot be found by name, or cannot be deleted | Slide-ins have **no name**: they are keyed by `SlideinType` (`Top`/`Bottom`/`Left`/`Right`), and `Hmi.Screen.ScreenSlidein` carries `Export` but **no `Delete`**. | Address them as `<device>/HMI/ScreenSlideins/<SlideinType>`. To remove one, the user does it in TIA - Openness cannot. Do not report the path as missing. |
| Looking for Classic alarms, recipes, reports, logging, user management, or scheduled tasks in the Openness object model | They are **not there**: those namespaces ship enums only, with no classes at all (`Siemens.Engineering.Hmi.Alarm/Recipe/Report/Logging/MenuToolbar`). | Configure them in TIA or through a verified project/library workflow, and say so plainly. Do not probe for `hmiTarget.Alarms`-style members. |
| A gauge or clock screen item is rejected over its size | Gauge/Clock size properties are **dependent**; TIA rejects an explicit `Width`/`Height` on import (a square box too, measured). | Omit the size and let TIA derive it - both generators already do. |
| You completed a related batch of Unified HMI objects and need engineering acceptance | `ok: true` from the creating call is not correctness. The vendor's own check is manual 5.13.2.2: a validatable object's `Validate()` returns per-property errors, and objects without that member (System Tags, Tag Tables) simply cannot be checked this way. | Collect the changed object paths and call `tia_openness_validate_hmi_objects` once for the batch; read `properties[].propertyName` / `errors`. After related tags, bindings and screens are complete, compile the affected HMI once with `tia_openness_compile(scope=target)`, before delivery or Runtime. Default mutation receipts defer compilation (`compileDeferred=true`, `engineeringValid=null`); continue building instead of recompiling or recreating each object. Fix reported errors together before recompiling: **a clean validation is not a compile** - they are separate verdicts and both matter. |
| A Unified object kind (e.g. `logging-tag`) is refused with `TIA_HMI_UNIFIED_VENDOR_BOUNDARY` | Final, and the message names the measured reason: the V20 `HmiSoftware` exposes **no `LoggingTags` composition at all**, `AuditTrails` has no name-taking `Create`, System Tags are read-only. | Do what the message says (log through a data log or the tag's own logging settings) or create the object in TIA. **Do not rotate `kind` names hoping one is accepted**, and do not substitute a data log while calling it logging tags. |
| An **illuminated button** or a **faceplate instance** screen item is refused, or TIA answers `The type of the argument 'ScreenItems' (Siemens.Engineering.Hmi.Screen.IlluminatedButton) is invalid.` | Both are FINAL for the XML route, measured on two panel families: the illuminated button is **not a `ScreenItems` member at all** on a Comfort panel (TP700) *or* on a Mobile panel (KTP400F) in a V18 portal - the same sentence both times, so the family table's "Mobile = Yes" does not make it importable. A faceplate instance needs a faceplate TYPE that already exists, and a wrong `FaceplateTypeName` fails at Create and **takes the TIA Portal process down with it** (measured). | Create them **in TIA on the panel that supports them**, then export that real screen and edit the export. Do not hand-write either shape, and do not read the family table as permission to import. |
| You need the mapping table of a Unified dynamization (range colours, bit-driven visibility) | Manual 5.13.2.3 needs a dynamization to exist FIRST, and on V20 the bit rows are **pre-created with it**: `Create(BitDynamizationType.SingleBit)` answers "Single bit entries are already created", the row type is `MappingTableEntryBitmask` with a writable `Condition` (there is no `Update(condition, relevant)`), and `From`/`To` are dynamically typed slots that reject a string. | Sequence: `tia_openness_create_hmi_dynamization` (creates the TagDynamization, binds the tag only when the object exposes exactly one Tag-bearing property) → `tia_openness_configure_hmi_mapping_table` (one row per call; it reuses the pre-created bit rows and writes `Condition`) → `tia_openness_validate_hmi_objects` → `tia_openness_compile`. The tools already handle all three version quirks; do not "fix" them by hand-writing values. |
| A CPM object instance cannot be created: `No CPM Type fond for the given cpm plant ObjectType name` | Final and environmental: the **project defines no such CPM type**, and Openness has **no API to create one** - both V20 and V21 expose only `PlantObject / PlantObjectInterface / PlantView / PlantViewNode / PlantViewsProvider` under `HmiUnified.Cpm`, with no type-create class. | Make the plant view and its plain nodes with `tia_openness_plant_view` (that part is verified), and get the CPM **types** from the project's plant model or a library. Do not keep inventing type names, and do not report the plant-view feature as broken because of it. |
| V21: the plant view answers `TIA_PLANT_VIEW_COMPOSITION_NOT_FOUND` even though V20 worked | **The route moved, not the feature.** V21 puts the Unified types in their own assembly (`Siemens.Engineering.WinCCUnified.dll`); the V20 sample's `Projects[0].PlantViews` property is gone and `PlantViews` is declared on `Siemens.Engineering.HmiUnified.Cpm.PlantViewsProvider`, which the project hands out as a **service** (`Project` implements `Siemens.Engineering.IEngineeringServiceProvider`). Measured by reflecting Portal V21's PublicAPI and then live: `create` → `create-node` → `list` → `delete` all work. | Nothing to do: the tool probes both routes and reports the one that answered as `plantViewRoute` (`Project.PlantViews` on V20 and earlier, `Project.GetService<PlantViewsProvider>().PlantViews` on V21). If it fails it now lists every probed route, so do not go hunting for the property again. Note `hierarchyPath` reads empty on V21 while `viewPath` is correct - version behaviour, not a missing node. |
| A freshly added **V21 Unified Comfort panel** compiles with exactly two errors about a password (`The entered password confirmation does not match the password.` / `The entered password does not comply with the password security concept: ...`) | Same class as the Classic start screen: a **device-level default of the new panel**, present before PLC Code writes anything, and the V21 Unified API exposes **no writable password member** (only `EnableUsernameAndPasswordAuthentication`; measured by reflecting `Siemens.Engineering.WinCCUnified.dll`). This is **not** a Unified-wide condition: a V20 Unified RT PC station (`SCADA_PC/HMI`, 14 screens, 9 tags, 3 connections) compiled **0 errors / 0 warnings** in the same round. | Fix it once in TIA (panel > Runtime settings) and recompile, or start from an already-configured panel/master copy. Do not chase API members. Everything the HMI tools wrote compiled **clean** next to it. |
| A mapping-table range row compiles into `Invalid range - the from or to value exceeds the limit for this data type`, or the compile warns `The range entries of the '...' property overlap.` | Range values are validated against the **dynamized tag's data type**, not the screen box: on V21 a `1..5` range on a **BOOL** tag is an ERROR, `10..20` on an **INT** tag is clean, and two rows covering the same values only produce a WARNING (measured 2026-09-16). | Pick ranges that fit the tag, and use `action=delete-row` (by `row_index`, `from`+`to`, or `all=true`) to take a wrong row out again - the readback prints every row's `index`. `condition`/`relevant` belong to the bit modes; a `mode=range` call that passes them now says so under `skipped` instead of dropping them silently. |
